# PDF Report

Консольное приложение на C#/.NET для анализа DICOM-данных плана лучевой терапии и формирования PDF-отчёта в стиле Monaco.

Проект читает `RTPLAN`, `RTDOSE` и `RTSTRUCT`, рассчитывает DVH и дозиметрические показатели, применяет клинические критерии для PTV и органов риска, строит DVH-график и формирует итоговый PDF-отчёт.

> **Статус проекта:** активная разработка. Текущая версия является рабочим прототипом и основой для дальнейшего выделения Application Service и формализации архитектуры.

## Возможности

- автоматический поиск `RTPLAN`, `RTDOSE` и `RTSTRUCT` в выбранной папке;
- чтение геометрии структур из RTSTRUCT;
- чтение трёхмерной сетки дозы из RTDOSE;
- чтение параметров полей и MU из RTPLAN;
- извлечение информации о фракционировании из RTPLAN;
- воксельный расчёт кумулятивного DVH;
- расчёт дозиметрических показателей PTV:
  - D2%;
  - D5%;
  - D50%;
  - D95%;
  - D98%;
  - HI ICRU;
  - HI D5/D95;
  - CI;
  - GI;
- импорт дозиметрических критериев из Monaco JSON;
- определение применимых PTV по наличию критерия `D50% >= Rx Gy`;
- оценка критериев для органов риска (`Dmax`, `Dmean`, `Dxx%`, `Dxx cm³`, `VxGy`);
- формирование статусов Pass / Warning / Fail;
- построение кумулятивной DVH с отображением Rx для PTV;
- генерация многостраничного PDF-отчёта через QuestPDF.

## Текущий pipeline

```text
DICOM folder
   │
   ├── RTPLAN ───────► beams / MU / fractions
   ├── RTDOSE ───────► 3D dose grid
   └── RTSTRUCT ─────► ROI contours
                         │
                         ▼
                   DVH calculation
                         │
              ┌──────────┴──────────┐
              ▼                     ▼
         PTV analysis           OAR analysis
              │                     │
              └──────────┬──────────┘
                         ▼
                    DVH plot
                         │
                         ▼
                    PDF report
```

Дополнительно приложение получает Monaco JSON с дозиметрическими критериями. Сопоставление имён структур выполняется после нормализации регистра и удаления пробелов, `_`, `-` и `.`.

## PTV

В текущей реализации структура рассматривается как кандидат PTV, если её имя содержит `PTV`.

Для включения PTV в клинический анализ дополнительно требуется:

1. найти соответствующую структуру в Monaco JSON;
2. найти для неё критерий вида `D50% >= Rx Gy`;
3. использовать значение этого критерия как Rx для данного PTV.

Если такой критерий отсутствует, PTV не включается в таблицу PTV-критериев отчёта.

### Критерии PTV

Сейчас используются следующие правила:

| Метрика | Критерий |
|---|---|
| D95% | `>= 95% Rx` |
| D50% | `>= 100% Rx` |
| D2% | `<= 107% Rx` |
| D2% warning | `>107%` и `<=110% Rx` |
| HI ICRU | `<= 0.15` |
| HI D5/D95 | `<= 1.10` |
| CI | `>= 0.7` |
| GI | `<= 3.5` |

CI и GI рассчитываются с использованием DVH всего dose volume (`Patient DVH`).

## Органы риска

Критерии OAR загружаются из Monaco JSON и преобразуются в `OarCriterion`.

Поддерживаемые типы метрик:

- `Dmax`;
- `Dmean`;
- `Dxx%`;
- `Dxx cm³`;
- `VxGy` с результатом в `%` или `cm³`.

Примеры:

```text
Dmax <= 54 Gy
Dmean <= 35 Gy
D2cm3 <= 45 Gy
V20Gy <= 65 cm3
```

## PDF-отчёт

Текущий отчёт содержит:

1. данные пациента;
2. предписание и фракционирование;
3. параметры полей;
4. дозиметрические критерии PTV;
5. таблицу органов риска;
6. DVH-график;
7. страницу комментариев и подписей.

PDF формируется библиотекой QuestPDF.

Для текущего шаблона отчёта требуется файл `logo.jpg`, доступный приложению во время генерации PDF.

## Структура проекта

### DICOM / Infrastructure

- `DicomDoseVolume.cs` — чтение RTDOSE и преобразование dose grid в Gy;
- `DicomStructureSet.cs` — чтение ROI и контуров RTSTRUCT;
- `DicomPlanReader.cs` — чтение параметров полей и MU;
- `DicomPrescriptionExtractor.cs` — чтение Dose Reference / фракционирования;
- `DoseReferenceReader.cs` — дополнительная модель чтения Dose Reference.

### Geometry / DVH

- `RoiGeometry.cs` — геометрические операции ROI;
- `DVHCalculator.cs` — воксельный расчёт DVH;
- `DVHResult.cs` — модель результата DVH;
- `DVHExtensions.cs` — дополнительные операции над DVH.

### PTV

- `PTVRxInfo.cs` — модель Rx;
- `PTVMetrics.cs` — рассчитанные показатели PTV;
- `PTVMetricsCalculator.cs` — расчёт Dxx, HI, CI и GI;
- `ClinicalRules.cs` — клиническая оценка PTV.

### OAR / Criteria

Основной текущий путь:

- `OarCriterion.cs`;
- `OarClinicalRules.cs`;
- `MonacoCriteriaModels.cs`.

В проекте также пока сохранена более ранняя система критериев:

- `DoseConstraint.cs`;
- `JsonCriteriaParser.cs`;
- `OarCriteriaEvaluator.cs`.

Она не является основным путём генерации текущего отчёта и рассматривается как кандидат на удаление/рефакторинг.

### Presentation

- `DvhPlotter.cs` — построение DVH через ScottPlot;
- `MonacoLikeReport.cs` — генерация PDF через QuestPDF;
- `PassFailResult.cs` — результат проверки клинического критерия.

### Orchestration

- `Program.cs` — текущая точка входа и orchestration всего use-case анализа плана.

В дальнейшем orchestration планируется перенести из `Program` в отдельный Application Service.

## Сборка

```bash
git clone https://github.com/mesava/PDF-Report.git
cd PDF-Report
dotnet restore
dotnet build
```

Запуск:

```bash
dotnet run
```

После запуска приложение последовательно запросит:

- папку с DICOM;
- папку с JSON-критериями;
- имя пациента;
- ID пациента;
- ФИО исполнителя;
- ФИО проверяющего;
- радиотерапевта.

PDF и DVH PNG в текущей реализации сохраняются на рабочий стол пользователя с именем на основе пациента и текущей даты.

## Технические особенности и известные ограничения

### DVH

DVH рассчитывается непосредственно по dose grid RTDOSE. Для каждого voxel center проверяется принадлежность ROI.

Текущая реализация требует дальнейшей валидации на расширенном наборе клинических планов, особенно для:

- структур с несколькими отдельными контурами на одном Z-срезе;
- ROI с отверстиями и сложной топологией;
- несовпадения Z-позиций RTDOSE и RTSTRUCT;
- нестандартной ориентации пациента / dose grid;
- сравнения рассчитанных объёмов и DVH с Monaco.

### Обработка структур вне dose grid

Если для структуры не найдено ни одного voxel dose grid, `DVHCalculator` генерирует исключение. В текущем `Program` ошибки расчёта отдельных структур перехватываются, поэтому такая структура пропускается, а анализ остальных структур продолжается.

Это поведение необходимо в дальнейшем сделать явным через диагностический результат, а не через подавление исключений.

### Monaco JSON

Сейчас приложение использует первый найденный `.json` в выбранной папке. Выбор конкретного набора критериев и валидация содержимого пока не вынесены в отдельный сервис.

### Prescription

Rx конкретного PTV определяется из Monaco-критерия `D50% >= Rx Gy`. RTPLAN используется для получения доступной информации о фракционировании и Dose Reference.

При нескольких PTV текущую логику отображения общего предписания в шапке отчёта необходимо дополнительно формализовать.

## Архитектурное развитие

Ближайшее направление рефакторинга — выделение Application Layer.

Планируемая схема:

```text
CLI / UI
   │
   ▼
PlanAnalysisService
   │
   ├── DICOM loading
   ├── Criteria loading
   ├── DVH calculation
   ├── PTV evaluation
   ├── OAR evaluation
   └── PlanAnalysisResult
             │
             ├── DVH plot
             └── PDF report
```

Цель — сделать так, чтобы `Program` отвечал только за взаимодействие с пользователем и запуск use-case, а расчётная и клиническая логика могла независимо использоваться из CLI, GUI, API или другого интеграционного слоя.

## Приоритеты дальнейшего развития

5. убрать дублирование геометрической логики;
6. заменить подавление исключений структур на диагностические статусы;
7. добавить unit/integration tests;
8. провести систематическую валидацию DVH и дозиметрических метрик относительно Monaco;
9. удалить неиспользуемые legacy-зависимости и классы;
10. подготовить архитектуру к GUI/API и дальнейшей интеграции.

## Важное замечание

Проект работает с медицинскими DICOM-данными и рассчитывает клинически значимые дозиметрические показатели. Любые изменения алгоритмов DVH, геометрии ROI, Rx или клинических критериев должны проходить отдельную проверку и валидацию перед использованием результатов в клиническом процессе.
